Google Drive is upload backup, not bidirectional editing. It now verifies TLS against the embedded Google Trust Services roots from https://pki.goog/roots.pem (retrieved 2026-11-14). Firmware releases must refresh this trust set. Sync requires a valid system clock; the device requests network time first if needed and stops if time/certificate checks fail. No insecure fallback exists.

Existing gdrive.cfg credentials/folder remain compatible. SHA-256 and remote IDs are retained under /journal/config/drive. A Google file ID is generated and saved before upload; retry after a lost response uses the same ID, preventing another copy. Changed files are PATCHed and unchanged files skipped. appProperties.tinyJournalPath preserves category identity. Existing duplicates from older firmware are not removed or adopted. A removed or inaccessible remote file reports an error rather than silently creating a replacement. Back up the Drive state with the SD card. Do not delete that state as an ordinary cleanup operation.

Network receipt printing is plain text ESC/POS over TCP (default 9100). Set the printer host/IP and paper columns from Sync & connectivity -> Network printer setup. Print current note saves first, then queues an immutable snapshot. The background task keeps typing responsive. Jobs are bounded to a total 32 KiB queue and four queued jobs; a full queue reports failure instead of silently dropping lines. Print-on-Enter is opt-in; it queues the completed logical line. Later text edits cannot change already printed paper.

The printer stream selects CP437. UK pound and common Latin accents are mapped; unsupported characters print '?'. Confirm the printer actually supports ESC/POS and that its page 0 is CP437. No printer address is built into the firmware. A successful send reports 'Job sent' rather than claiming physical printing. After an interrupted send, inspect the printer before retrying because some paper may already have printed. Raw TCP printing has no TLS; use the trusted local network and do not expose the printer port to the internet.

Network printer configuration is JSON at /journal/config/printer.cfg:

    {"host":"YOUR_PRINTER_IP","port":9100,"columns":32,"printOnEnter":false,"cutAfterReceipt":true}

Validation: tests/printer_text_test.cpp tests the actual UTF-8 decoder, malformed input and CP437 mappings with a host C++ compiler. tests/probe_printer.py HOST only connects to TCP and sends no bytes. Google account sync and certificate-failure behaviour still require device/network acceptance testing; host tests do not substitute for them. Device printing was subsequently verified as described below.

Additional validation: tests/printer_tcp_test.cpp includes the actual JournalPrinter header with Arduino/FreeRTOS shims and sends its output to a loopback TCP server. It checks the complete ESC/POS prefix (CP437 selection), pound encoding, stripping embedded ESC control characters, empty-host rejection and the 32 KiB limit. This validates encoding and checked TCP writes, not FreeRTOS scheduling or physical printer behaviour. The embedded CA set also successfully validated both OAuth and Drive endpoint TLS using curl --cacert, with no credentials sent (unauthenticated HTTP 404/403 responses).

Follow-up: completed receipts now feed to the cutter and send ESC/POS `GS V 66 0` (partial cut), enabled by default and configurable with `cutAfterReceipt`. Live lines do not cut. The prior code immediately disconnected Wi-Fi on a completion notification; that could interrupt a newly queued job and did not allow pending TCP traffic time to drain. Radio release is now deferred, checked against the current queue, and cancelled by a new job. Time sync/Wi-Fi scans cannot interrupt a print queue. USB acceptance builds expose `PRINTERSTATUS` with phase/result/byte counts, never credentials, so a Wi-Fi setup failure can be distinguished from an unreachable printer or partial transfer.

Connected-device acceptance: the Cardputer sent a canned 63-byte receipt to the configured printer, reporting Wi-Fi connected and all bytes sent. The user confirmed that the receipt printed and cut. This verifies this printer and receipt path; it does not make TCP success a general guarantee of physical output.
